# WindowsProtect setup window (0.5.7-test)

New installations start a fixed four-hour window when installation of protection components begins. HKLM stores the original UTC deadline; retries, repairs, reopening setup, and restarts do not renew it. Already-active installations remain active and do not receive a fresh setup window.

Setup verifies a live approved desktop stream and a fresh command round trip to this PC. On success it marks support verified and displays **Installed — waiting for dashboard activation**. UltraViewer and other listed remote tools remain available during the pending window. The dashboard shows the reported deadline and a countdown; it refreshes every 30 seconds.

**Activate protection** rechecks the PC's recent enrolled support identity, desktop stream, and fresh local command proof. A fixed command requests activation. The local service checks the matching proof, activates blocking, and reports protected through heartbeat. The dashboard reports **Activation requested**, not Protected, until the PC confirms. Activating disconnects blocked remote tools. There is no dashboard deactivation control.

When the four-hour deadline is reached, the local service activates protection even without the dashboard, internet connectivity, or successful support verification. This deadline intentionally takes priority over keeping UltraViewer available. If the PC is powered off, it activates on the next service start after expiry. The independent local policy timer checks each second and kills blocked processes without network calls; heavy maintenance/telemetry remains every 30 seconds. PowerShell helper waits are bounded. A monotonic clock and persisted last-observed time resist ordinary clock rollback; a local administrator can still tamper with the machine or stop its service. This is not tamper-proof endpoint enforcement.

Bulk actions select 1–100 visible devices. Activation uses up to three independent per-PC requests concurrently; each must verify its own support proof, and failures are reported individually. Deletion requires confirmation, runs one ID-filtered DELETE, and reports only rows actually removed. Deleting dashboard records revokes monitoring via those enrollment tokens and removes related records according to existing database foreign keys. It does not uninstall WindowsProtect, disconnect approved support, or turn off local protection. No database schema change is required; the existing migration_status text field carries the window phase and UTC deadline.

Automated checks cover real Windows password acceptance/rejection, persistent deadline/no extension, verified setup staying pending, fresh manual activation proof, offline expiry, active upgrades, bulk ID validation, admin authentication/origin checks, filtered deletion, fresh online identity, and desktop protocol fixtures. A disposable Windows PC must still test the live support server and UltraViewer handover end to end. Builds are unsigned unless trusted signing has been configured.

## Remote uninstall (0.5.8-test)

The dashboard has a distinct **Uninstall from PC and delete** action. Multi-select sends one authenticated request per PC and displays per-PC outcomes. Only agents 0.5.8 or newer accept the operation. Older PCs must be updated first; an offline updated PC can be queued immediately. A random request ID is stored in the existing migration_status field. Heartbeats use a conditional update and retry status races, preserving pending uninstall and delivering the ID only to that PC's enrollment token. Ordinary record deletion and activation are rejected while uninstall is pending.

The service stages a verified embedded remover in a SYSTEM/admin-only folder and creates a SYSTEM retry task every five minutes. It copies only the encrypted device token and removal metadata. The remover authenticates the matching queue before making changes. If the owner does not choose Skip, setup verifies the Windows password and stores it only on that PC using machine-scoped Windows DPAPI for the optional one-time remote-unlock credential provider. The dashboard sends only a random two-minute request; it never receives the password. Built-in Windows sign-in providers are never filtered. Removal unregisters the provider and deletes its encrypted secret before deleting program files. The remover also clears the legacy WindowsProtect credential left by older versions when one exists.

After credential cleanup, the worker stops/disables/deletes the WindowsProtect service, removes its exact Run entry/helper processes, deletes its actual installation and data directories and HKLM settings, then invokes the approved support agent's official full uninstall. Support paths must match recognized isolated Program Files Mesh Agent directories; unexpected locations fail safely. It checks services, matching helper/support processes, files and settings before reporting completion. Only a matching enrolled token/request with all cleanup flags can delete the record. If confirmation fails, the detached worker retries and keeps the dashboard record. Its private staging folder and scheduled task are removed after acknowledgement. A completion marker handles a lost deletion acknowledgement without starting removal on an unauthenticated request.

Defender, firewall, UAC and other Windows security protections remain enabled. Removal does not reinstall or re-enable previously blocked third-party tools. A leftover downloaded setup EXE and external MeshCentral server history are outside the installed-PC cleanup scope.

Tests cover unauthorized and partial confirmations, token/ID binding, queueing offline PCs, concurrent heartbeat preservation, deletion filters, the real Windows credential deletion API on a disposable fixture, safe support-path validation, fixture directory deletion and timeout handling. A live disposable-PC uninstall test is still required before rollout.
